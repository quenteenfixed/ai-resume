inspect-ai 框架概述

Inspect 是一个面向大语言模型评估的开源 Python 框架，由 UK AI Security Institute（英国 AI 安全研究所）与 Meridian Labs 联合开发。官方定位为"an open-source framework for large language model evaluations"， 支持 coding、agentic tasks、reasoning、knowledge、behavior、多模态理解等多种评估场景。

核心设计哲学

  • 评估是可组合的 — Dataset、Agent、Tool、Solver、Scorer 均为可复用构件，自由组合
  • 从简单生成到复杂智能体统一建模 — 简单任务用 generate()，复杂任务用 ReAct / Deep Agent / 多 Agent
  • 评估即工程 — 强调可复现运行、日志、trace、metrics、可视化、调试
  • 支持前沿模型与安全评估 — 不仅评估 accuracy，也评估 agent 行为、工具调用、沙箱逃逸、prompt injection
  • 统一模型接口 — 支持 OpenAI、Anthropic、Google、Mistral、DeepSeek、Grok、vLLM 等多 provider
关键定位

Inspect 不是一个 RL 训练框架（不提供 PPO/DPO/GRPO），也不是一个 agent 开发框架（不替代 LangChain/CrewAI）。 它的核心定位是 "LLM/Agent evaluation operating system + benchmark framework + trace/scoring infrastructure" — 即 LLM 和 Agent 的工程化评估操作系统。

inspect-ai 核心架构：Task / Solver / Scorer

Inspect 的核心评估单元是 Task，由三个可组合构件构成：

┌─ inspect-ai 核心评估架构 ─────────────────────────────────┐ │ │ │ Task │ │ ├── Dataset │ │ │ ├── Sample(input, target, metadata, files) │ │ │ ├── 来源: CSV / JSON / HuggingFace / S3 / 自定义 │ │ │ └── 支持多模态 (图片, 音频, 视频) │ │ │ │ │ ├── Solver ← "the heart of Inspect evaluations" │ │ │ ├── generate() → 简单生成 │ │ │ ├── chain_of_thought() → CoT 推理 │ │ │ ├── use_tools() → 工具调用 │ │ │ ├── self_critique() → 自我批评 │ │ │ ├── react() → ReAct Agent (工具循环) │ │ │ ├── deepagent() → Deep Agent (长周期任务) │ │ │ ├── handoff(agent) → 多 Agent 交接 │ │ │ └── as_tool(agent) → Agent 作为工具 │ │ │ │ │ └── Scorer │ │ ├── match() → 文本匹配 │ │ ├── exact() → 精确匹配 │ │ ├── model_graded_qa() → LLM 评分 │ │ ├── model_graded_fact() → 事实判断 │ │ ├── math() → 数学等价 │ │ ├── f1() → Token overlap │ │ └── custom scorer → 自定义异步评分函数 │ │ │ │ 运行时能力 │ │ ├── Sandbox: Docker / Kubernetes / Modal / Proxmox │ │ ├── Parallelism: 异步并行, max_samples, max_sandboxes │ │ ├── Logging: transcript, Inspect View, VS Code extension │ │ ├── Control Channel: 运行中可观察 task/sample 状态 │ │ ├── Scanners: 检测 refusal, eval awareness, reward hacking │ │ └── Model Roles: task model, grader model, scanning model │ │ │ └────────────────────────────────────────────────────────────┘

最小评估示例

from inspect_ai import Task, task
from inspect_ai.dataset import Sample
from inspect_ai.solver import generate, use_tools
from inspect_ai.scorer import match

@task
def addition_problem():
    return Task(
        dataset=[Sample(input="What is 1 + 1?", target=["2"])],
        solver=[use_tools(add()), generate()],
        scorer=match(numeric=True),
    )

Agent 作为 Solver 的模式

from inspect_ai.agent import react
from inspect_ai.tool import web_search

agent = react(
    name="web_surfer",
    description="Web research assistant",
    prompt="You are an expert at using a web browser.",
    tools=[web_search()],
)

# Agent 可直接作为 solver 使用
eval("research_bench", solver=agent)

多 Agent 交接模式

from inspect_ai.agent import handoff
from inspect_ai.solver import use_tools, generate

# handoff() 传递完整对话历史
# as_tool()  简单 string-in / string-out
eval(
    task="research_bench",
    solver=[
        use_tools(addition(), handoff(web_surfer())),
        generate()
    ]
)
架构洞察

inspect-ai 的 handoff() 和 as_tool() 原语提供了多 Agent 委派的基础能力。 Andon Labs 的 multiagent-inspect 正是在此基础上扩展了更完整的多 Agent 通信机制 — 允许 Agent 启动子 Agent、查询子 Agent 状态、与子 Agent 对话，而不仅仅是单向交接。

README 核心说明

# multiagent-inspect

Multi-agent system for AI evaluations in AISI's inspect-ai framework

We provide a set of tools which allow agents to delegate tasks to sub-agents.
Specifically, the init_sub_agents function returns three tools:
- sub_agent_specs: Return info about the sub-agent(s)
- run_sub_agent: Give string input to one sub-agent and execute it.
- chat_with_sub_agent: Ask questions to the sub-agent to find what it did.

关键发现

multiagent-inspect 不是独立的多 Agent 框架，而是围绕 inspect-ai 的 Solver、Tool、Model、Store、Transcript API 构建的扩展层。它直接使用 inspect-ai 的 @tool 装饰器定义工具、使用 store 管理状态、 使用 get_model() 获取模型实例、使用 call_tools() 执行工具调用。 这说明 Andon Labs 完全拥抱了 inspect-ai 的架构范式。

5.2 三个核心工具解析

sub_agent_specs

  • 返回子 Agent 的配置信息
  • 让主 Agent 了解可用的子 Agent 能力
  • 类似 inspect-ai 的 as_tool()，但更丰富
  • 支持查询多个子 Agent 的规格

run_sub_agent

  • 向子 Agent 发送 string 输入并执行
  • 子 Agent 独立运行，有自己的对话历史
  • 类似 inspect-ai 的 handoff()，但支持独立上下文
  • 执行结果返回给主 Agent

chat_with_sub_agent

  • 向子 Agent 提问，了解其之前的执行情况
  • 这是 inspect-ai 原生不具备的能力 — 原生 handoff() 是单向交接，无法回溯
  • 支持主 Agent 与子 Agent 的双向通信
  • 用于长周期任务中的上下文同步和状态查询
  • 是 Vending-Bench 长周期多 Agent 协作的关键机制
需注意

inspect-ai 原生的 handoff() 和 as_tool() 只支持单向委派（主 Agent → 子 Agent）， 子 Agent 执行完毕后结果返回，但主 Agent 无法在子 Agent 执行过程中与其交互。 Andon Labs 的 chat_with_sub_agent 扩展了这一能力，实现了 Agent 间的双向通信， 这是长周期自治智能体的关键需求。

07

Drone-Bench 与 Blueprint-Bench：是否使用 inspect-ai

调研结论

Drone-Bench 和 Blueprint-Bench 的公开页面中未找到任何直接引用 inspect-ai、AISI 或 Inspect 的证据。

Drone-Bench

  • 无人机导航任务评测
  • 五类任务：reconstruction, localization, navigation, detection, following
  • 以人类 baseline 评分
  • 页面无 inspect-ai 引用 无证据
  • 可能使用自定义评测框架或基于其他工具

Blueprint-Bench 2

  • 从公寓照片生成 2D floor plan
  • 50 套公寓，每套约 20 张室内照片
  • Agent 使用 persistent notepad
  • 评分基于连通图、房间数、门数、密度、方向
  • 页面无 inspect-ai 引用 无证据
推断

Andon Labs 可能在 Vending-Bench（长周期多 Agent 文本任务）中选择了 inspect-ai，因为这类任务天然契合 inspect-ai 的 Solver/Tool/Scorer 范式。而 Drone-Bench（无人机物理模拟）和 Blueprint-Bench（图像处理） 涉及更多物理/视觉层面的交互，可能需要不同的评测基础设施，因此不一定基于 inspect-ai。 这说明 inspect-ai 的适用边界主要在文本/工具驱动的长周期 Agent 评测。

结论

如果目标是评估 Agent 的长周期能力（而非开发 Agent 应用），inspect-ai 是目前最成熟的开源选择。 Andon Labs 的选型验证了这一点 — 他们不需要自研评估基础设施，而是利用 inspect-ai 已有的能力， 只在多 Agent 通信这一关键缺口上扩展。

基于 inspect-ai 的团队技术方案设计

基于以上调研，为团队设计一套基于 inspect-ai 的长周期自治智能体评测与运行技术方案。 方案分为三个层次：评测框架层、Agent 运行时层、业务工具层。

方案设计原则

  • 不重复造轮子 — 评估基础设施完全使用 inspect-ai，只在关键缺口处扩展（参考 Andon Labs 策略）
  • 业务系统即 Tool — 将 6 个现有 AI 产品封装为 inspect-ai @tool，通过 call_tools() 被 Agent 调用
  • 分层模型路由 — 通过 inspect-ai get_model() 按任务复杂度切换 LLM，控制成本
  • 多 Agent 通信 — 参考 multiagent-inspect 实现 run_sub_agent + chat_with_sub_agent
  • 沙箱隔离 — 使用 inspect-ai Docker sandbox 隔离每个业务 Agent
  • 可信度分析 — 使用 inspect-ai Scanners 检测 reward hacking、refusal、eval awareness
  • 日志即审计 — inspect-ai Transcript + 不可变审计日志 = 完整行为追溯
