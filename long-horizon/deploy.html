执行摘要与目标

基于 Andon Labs 从 Vending-Bench 论文到 Pion 平台的 19 个月技术演进分析， 本方案将吸纳其分层治理、专业分工、运行时安全、分层记忆四大核心理念， 为团队设计一套可落地的长周期自治智能体系统。

设计原则

  • 业务导向：工具围绕业务动词设计，而非围绕 API 设计
  • 分层治理：人类 → 监督Agent → 主Agent → 子Agent 四层架构
  • 安全先行：运行时 Guardrail 与 Agent 同步开发，而非事后补丁
  • 渐进增强：四阶段交付，每阶段可独立验证
  • 真实优先：尽早接入真实系统（邮件、银行、ERP），而非长期在模拟环境中验证
核心借鉴

Andon Labs 最值得借鉴的不是某个算法，而是工程体系： 让 Agent 在真实约束下长期承担责任的整套基础设施。 本方案的每一步设计都围绕"能否在真实环境中长期运行"来展开。

03

四阶段实施路线图

按优先级分为四阶段，每阶段可独立交付和验证：

Phase 0 基础设施层 第 1-3 周
目标：搭建 Agent 运行的底层基础设施。
交付物：容器化运行时、状态持久化、基础工具注册表、健康监控、日志审计。
验证标准：一个最简 Agent 可在容器中持续运行 72 小时不崩溃，状态可恢复。
Phase 1 核心Agent引擎 第 4-8 周
目标：单 Agent 长周期稳定运行。
交付物：分层压缩记忆系统、事件驱动调度（wait time）、业务导向工具系统、上下文溢出自动压缩。
验证标准：Agent 能在 200k token 上下文限制下连续运行 7 天，记忆压缩正确触发，关键状态不丢失。
Phase 2 多Agent协作层 第 9-12 周
目标：主Agent + 专业子Agent + 临时子Agent 协作体系。
交付物：子Agent管理器（spawn/监控/结果汇总）、持久专业子Agent（采购/财务/营销/运营）、Fan-out 并行子Agent、Agent间结构化通信。
验证标准：主Agent 能并行 fan-out 5个子Agent 做供应商调研，结果正确汇总，子Agent 异常不影响主Agent。
Phase 3 治理与安全层 第 13-16 周
目标：监督Agent + 运行时Guardrail + 人类升级通道。
交付物：Supervisor Agent（Andonos式）、行为监控引擎、规则引擎、违规警告系统、人类介入通道、敏感信息脱敏、权限隔离。
验证标准：Agent 违规时（如超预算采购）能被自动检测并警告，严重违规能升级人类介入，敏感信息不泄露。
阶段依赖关系

Phase 0 → Phase 1 → Phase 2 为强依赖链，必须顺序执行。 Phase 3 的部分工作（如规则定义）可与 Phase 2 并行启动， 但 Supervisor Agent 需要 Phase 2 的多Agent架构完成后才能完整实现。

Phase 1：核心Agent引擎（第 4-8 周）

5.1 分层压缩记忆系统

这是 Andon Labs 技术演进中最重要的理念转变： 从 Vending-Bench 的三层存储（Scratchpad + KV + Vector DB） 转向 Andon Market 实际使用的分层压缩（Long-term + Short-term + Latest）。

上下文窗口（如 200k tokens） │ ├── Long-term Memory（长期记忆 — 压缩后注入） │ ├── 角色与使命 # "你是XX Agent，负责YY" │ ├── 核心政策与约束 # 不可违反的规则 │ ├── 关键实体信息 # 公司/账户/人员/系统 │ └── 历史重要决策 # 过去做过的关键决定 │ ├── Short-term Memory（短期记忆 — 压缩后注入） │ ├── 当前任务状态 # 正在做什么、进度如何 │ ├── 近期关键事件 # 今天发生了什么 │ ├── 待处理事项 # 等待中的订单/回复 │ └── 当前优先级 # 现在最重要的是什么 │ └── Latest Messages（最近消息 — 原文保留） └── 最近 N 条对话/工具调用结果 # 压缩触发：上下文使用量 > 阈值（如 150k / 200k） # 压缩方式：LLM 总结 + 结构化提取 # 注入位置：下一轮上下文顶部
# core/memory/hierarchical_memory.py class HierarchicalMemory: """分层压缩记忆系统 借鉴 Andon Market 实际方案：当上下文超阈值时自动压缩 """ def __init__(self, llm, max_context_tokens: int = 200000): self.llm = llm self.max_context = max_context_tokens self.compress_threshold = int(max_context_tokens * 0.75) # 150k self.long_term = {} self.short_term = {} self.latest_messages = [] async def add_message(self, message: dict): self.latest_messages.append(message) # 检查是否需要压缩 current_tokens = self._estimate_tokens() if current_tokens > self.compress_threshold: await self._compress() async def _compress(self): """核心压缩逻辑：将旧消息压缩为长期/短期记忆""" # 1. 分离：最近20条保留，其余进入压缩 to_compress = self.latest_messages[:-20] self.latest_messages = self.latest_messages[-20:] # 2. LLM 压缩为结构化记忆 compressed = await self.llm.compress( context=to_compress, current_long_term=self.long_term, current_short_term=self.short_term, prompt="""请将以下对话历史压缩为结构化记忆。 输出格式： long_term: - role: 角色与使命（不变的部分） - policies: 核心政策与约束 - entities: 关键实体信息（公司/账户/人员） - decisions: 历史重要决策 short_term: - current_task: 当前任务状态 - recent_events: 近期关键事件 - pending: 待处理事项 - priorities: 当前优先级 规则： - 长期记忆只保留不变或极少变化的信息 - 短期记忆保留当前可变状态 - 敏感信息（非团队成员姓名等）必须脱敏 """ ) # 3. 合并：新压缩的记忆与旧记忆合并 self.long_term = compressed["long_term"] self.short_term = compressed["short_term"] def build_context(self) -> str: """构建完整上下文：长期 + 短期 + 最近消息""" return f""" === 长期记忆 === {json.dumps(self.long_term, ensure_ascii=False, indent=2)} === 短期记忆 === {json.dumps(self.short_term, ensure_ascii=False, indent=2)} === 最近对话 === {self._format_messages(self.latest_messages)} """
反直觉设计要点

更大的记忆 ≠ 更好的表现（Andon Labs 在 Vending-Bench 中已验证）。 压缩记忆的核心不是"记住更多"，而是"记住更准"。 长期记忆只保留不变信息，短期记忆只保留当前状态，其余的果断丢弃。

Phase 3：治理与安全层（第 13-16 周）

7.1 Supervisor Agent（Andonos 式）

借鉴 Andon Labs 最具创新性的架构设计——用 Agent 监督 Agent：

# governance/supervisor_agent.py class SupervisorAgent: """监督型 Agent（Andonos 式） 位于人类和业务Agent之间，负责： - 监控行为与 system prompt 的一致性 - 检测偏离并警告 - 提供中立状态更新 - 严重时升级人类介入 """ def __init__(self, llm, rule_engine, human_channel): self.llm = llm self.rules = rule_engine self.human_channel = human_channel self._business_agents = {} # 监督的业务Agent self._warnings = {} # 警告历史 async def supervise(self, agent_id: str, agent_name: str): """持续监督一个业务Agent""" self._business_agents[agent_id] = agent_name while True: # 1. 获取 Agent 当前状态 state = await self._get_agent_state(agent_id) behavior = await self._get_recent_behavior(agent_id) # 2. 规则检查 violations = await self.rules.check(state, behavior) if violations: for v in violations: # 3. 先警告 Agent 自行纠正 await self._warn_agent(agent_id, v) # 4. 严重违规：升级人类 if v.severity == "critical": await self.human_channel.escalate( agent_name, v, state ) # 5. 生成中立状态更新（给人类） update = await self._generate_neutral_update(agent_id, state) await self.human_channel.report(update) await asyncio.sleep(300) # 5分钟一轮 async def _generate_neutral_update(self, agent_id, state) -> str: """生成中立状态更新，避免业务Agent自欺欺人 借鉴 Andonos "提供中立更新" 的设计 """ return await self.llm.summarize( prompt=f"""基于以下Agent状态，生成客观中立的状态报告： 业务目标：{state.get('goal')} 当前进展：{state.get('progress')} 近期决策：{state.get('recent_decisions')} 异常事件：{state.get('anomalies')} 要求： - 基于事实，不美化 - 如果发现偏离目标，明确指出 - 如果发现风险，明确标注 """ )

7.2 运行时 Guardrail 引擎

借鉴 Andon Market 的 Guardrail 系统，实现运行时行为监控：

# governance/guardrail/rule_engine.py from dataclasses import dataclass from enum import Enum class Severity(Enum): LOW = "low" # 警告Agent自行纠正 MEDIUM = "medium" # 警告 + 限制工具 HIGH = "high" # 警告 + 暂停操作 CRITICAL = "critical" # 升级人类介入 @dataclass class Rule: name: str description: str check_fn: callable severity: Severity class RuleEngine: """运行时规则引擎 借鉴 Andon Market Guardrail 持续比较行为与 system prompt """ def __init__(self): self._rules = [] def register(self, rule: Rule): self._rules.append(rule) async def check(self, state: dict, behavior: dict) -> list: violations = [] for rule in self._rules: if await rule.check_fn(state, behavior): violations.append(rule) return violations # 预置规则示例 engine = RuleEngine() engine.register(Rule( name="budget_limit", description="单次采购不超过预算上限", check_fn=lambda s, b: b.get("order_amount", 0) > s.get("budget_limit", 0), severity=Severity.HIGH, )) engine.register(Rule( name="no_unauthorized_contract", description="未经审批不得发送合同", check_fn=lambda s, b: b.get("action") == "send_contract" and not b.get("approved"), severity=Severity.CRITICAL, )) engine.register(Rule( name="sensitive_info_protection", description="不得在对外通信中暴露敏感信息", check_fn=lambda s, b: contains_sensitive(b.get("message_content", "")), severity=Severity.CRITICAL, )) engine.register(Rule( name="schedule_compliance", description="排班不得违反劳动规则（如连续超时）", check_fn=lambda s, b: violates_labor_law(b.get("schedule")), severity=Severity.MEDIUM, ))

7.3 人类介入通道

Agent 行为 ↓ Guardrail 规则检查 ├── LOW: 警告 Agent → Agent 自行纠正 ├── MEDIUM: 警告 + 限制部分工具 → Slack 通知 ├── HIGH: 警告 + 暂停操作 → Slack + 邮件通知 └── CRITICAL: 升级人类 → 电话/Slack 即时通知 → 等待人类决策

7.4 敏感信息脱敏

借鉴 Andon Market 记忆系统中的信息保护机制：

# governance/security/redactor.py class SensitiveInfoRedactor: """敏感信息脱敏：借鉴 Andon Market 非 Andon 员工姓名脱敏""" REDACTION_RULES = { "non_employee_names": True, # 非团队成员姓名替换 "bank_account_full": True, # 银行账号部分遮蔽 "personal_address": True, # 个人地址脱敏 "phone_numbers": True, # 手机号部分遮蔽 "passwords_tokens": True, # 密码/Token 完全遮蔽 } def redact(self, text: str, context: str) -> str: """根据上下文脱敏 context: "memory" | "external_comm" | "log" | "audit" """ # 对外通信：最严格脱敏 if context == "external_comm": text = self._redact_all(text) # 记忆存储：中等脱敏 elif context == "memory": text = self._redact_non_employees(text) return text

风险概率影响对策

最高优先级风险

Andon Labs 的经验表明：能力越强的模型，安全风险越高。 高绩效模型可能出现欺骗、权力寻求等行为。因此 Phase 3 的 Guardrail 系统 不能延后到全部功能完成后才做——规则定义应从 Phase 1 就开始，随业务功能同步迭代。
